# Panel review: reproducibility and software engineering

Reviewer role: reproducibility / software engineer (adversarial). Scratch: `/tmp/claude-0/.../scratchpad/panel-repro/`.
Everything below was run in this session against `data/FPA_FOD_20221014.sqlite` (SHA-256 `04f5ab8b...51a965a8`, verified) with `.venv/bin/python` (3.12.3, pandas 3.0.6, numpy 2.5.3, scikit-learn 1.9.1). Line references are to the working tree at commit `b52aff2`.

## (a) Verdict

The numbers reproduce; the engineering does not deserve the credit. I re-ran the pipeline end to end with `n_jobs` forced to 1 and got CV RMSE 6.3322 (+/- 0.1338), test RMSE 6.5957, MAE 1.3768, bit-identical to `outputs/reproduction_model.json`. That determinism comes from `random_state=42` and SQLite's rowid scan order, not from anything the repo guards. At the reviewed commit there are no tests, no CI, no schema check on the SQLite file, and `src/` has a library function that calls `sys.exit`, one-hot columns that change with the input, `fillna(0)` that would move a fire with no coordinates to the Gulf of Guinea, and plots written to whatever directory the caller is in. `requirements.txt` omits `pyarrow` that `build_cache.py` needs, and the committed notebook ran out of order on Python 3.14.2, so its figures cannot be tied to its metrics. The download script has no checksum and no resume. Fixable in a day; not yet portfolio grade.

## (c) Test plan (to be implemented by the testing agent)

Layout: `tests/` with `conftest.py`, run by `pytest -q` in CI on the pinned interpreter. Target run time under 60 s without the real data; a nightly job runs the full-data golden test.

1. **Synthetic SQLite fixture** (`tests/fixtures/make_fixture.py`, checked-in output `tests/fixtures/fires_small.sqlite`, ~2,000 rows). Built from the real schema (`CREATE TABLE [Fires]` copied verbatim from `sqlite_master` so the typed `check(...)` constraints are preserved), populated with a deterministic generator (seed 0) that covers: every one of the 13 `NWCG_GENERAL_CAUSE` values; at least one row per year 2008-2020 (so the 2010 filter is exercised); rows with `CONT_DATE` NULL; rows with negative duration; rows with `DISCOVERY_DOY` 366 in leap and non-leap years; a row with `FIRE_YEAR` disagreeing with `DISCOVERY_DATE`; a row with NULL lat/lon; a row with NULL cause; dates with 1- and 2-digit months and days. The fixture must also include a stub `Shape` column so `SELECT *` behaves like production.
2. **Unit tests for `preprocess_data`** (`tests/test_features.py`): fixed feature column list and order regardless of which causes are present (C1); leap-year cyclical encoding: `sin/cos` of 31 Dec in 2020 is within 1e-9 of 1 Jan, and 1 Mar 2019 equals 1 Mar 2020 (C4); missing lat/lon raises rather than becoming 0 (C2); NaN vs negative duration counted separately (C6); date format enforced (`'2020-01-02'` raises) (C5); dtypes of `X` and `y`; no leakage columns (`FIRE_SIZE`, `FIRE_SIZE_CLASS`, `CONT_*`) can survive even if passed in (C12); the function is pure (input frame unchanged).
3. **Loader tests** (`tests/test_io.py`): `load_data` on the fixture returns exactly the rows with `FIRE_YEAR >= 2010 AND CONT_DATE IS NOT NULL`, ordered by `FOD_ID`; missing file raises `FileNotFoundError`, not `SystemExit` (C7); schema validation rejects a fixture with a renamed column or wrong declared type (C8); hash mismatch is reported with both hashes; SQLite loader and Parquet loader return frame-equal `X, y` on the fixture (P8).
4. **Model plumbing tests** (`tests/test_model.py`): `build_model()` hyperparameters match the claims (100 trees, depth 10, seed 42); `train_model(..., out_dir=tmp_path)` writes only inside `tmp_path` and returns a metrics dict with the expected keys; two runs with `n_jobs=1` and `n_jobs=2` on the fixture give bit-identical predictions (D4); split is a deterministic function of `FOD_ID` (D5).
5. **Golden-numbers test** (`tests/test_golden.py`, marked `@pytest.mark.fulldata`, skipped unless `data/FPA_FOD_20221014.sqlite` exists and matches `data.sha256`): run the pipeline (`--skip-cv` variant under 3 minutes single-core) and assert `n_model == 630053`, `test_rmse == 6.5957 +/- 5e-4`, `test_mae == 1.3768 +/- 5e-4`, `predict_zero.mae == 1.0941 +/- 5e-4`, feature list equals the 17 names, plus the CV numbers when CV is enabled. Values come from `outputs/claims.json`, not from literals in the test.
6. **Claims-ledger test** (`tests/test_claims.py`): parse `README.md` (and every `site/*.html` once built) for tokens of the form `{{claim:<id>}}` or a numeric regex tied to an id table, and assert every number equals `outputs/claims.json[id].value` formatted with `claims.json[id].format`. Fail on any number in the README that is not backed by an id, and on any claim in the ledger whose `source` script/commit is missing. This makes "every README number regenerates" a mechanical property instead of a sentence in `REPRODUCTION.md`.
7. **Download-script tests** (`tests/test_download.py`): against a local `http.server` serving a small zip: partial download is resumed via `Range` (P3); a `.part` file is never renamed unless `Content-Length` matches; hash mismatch exits non-zero and removes the DB (P1); the zip member is chosen by name (P4); disk-space check aborts when a monkeypatched `shutil.disk_usage` reports too little.
8. **Notebook test** (only if the notebook is kept): `jupyter nbconvert --execute --to notebook` on the fixture with `WILDFIRE_DB_PATH` set; assert no cell errors and that the committed file has no outputs (`nbstripout --verify`).
9. **CI** (`.github/workflows/ci.yml`): matrix on Python 3.12 only (the pinned version); steps: install from `requirements.lock`, `ruff check`, `pytest -m "not fulldata"`, build the site from `outputs/claims.json`, and `git diff --exit-code outputs/claims.json site/` after a rebuild so committed outputs cannot drift from the code. A separate manual/nightly workflow with the data cached runs `pytest -m fulldata`.

Module boundaries: `analysis/` is a library with no side effects at import, no `sys.exit`, no `basicConfig`, no writes outside a passed `out_dir`. `scripts/` are the only entry points and the only place logging is configured. `outputs/claims.json` is the contract between analysis and presentation: README rendering, the site builder and the tests all read it and none of them recompute anything. The notebook is removed (or, if kept, lives under `notebooks/` stripped and executed in CI). `run_pipeline.py` becomes `python -m analysis` or `scripts/reproduce.py --part model`; keeping two entry points that do the same thing is how the notebook and the pipeline drifted.
